# Revision Hygiene

レビュー指摘に登場した概念を反転して成果物へ残すのではなく、修正後に成立すべき状態へ直接収束させる。検証のため一時的に確認することと、テスト、コメント、注記、ガード、互換層として恒久的に残すことを分ける。

## 役割とrouting

このSkillは、レビュー後の修正で何を恒久的に残すかを判断するoverlayである。成果物全体の構造設計、形式固有の品質、ファイル生成を単独では所有しない。

- 文章中心の文書で見出し、論証、読者動作、情報配置を改訂する場合は`document-authoring:text-document-architect`と併用し、文章構造と文書品質については同Skillを優先する。
- スライドでstoryline、pacing、本編・notes・Appendixの配置を改訂する場合は`document-authoring:presentation-architect`と併用し、発表構造とdeck品質については同Skillを優先する。
- DOCX、PPTXなどの生成、編集、render、形式検証には、利用可能なら形式固有のSkillを使い、その技術的な生成・検証要件を優先する。
- このSkillは、上記の作業でreviewにより不要になったテスト、説明、注記、互換層などを残すべきかだけを判断する。

レビュー結果の診断や報告だけを求められ、修正を依頼されていない場合はこのSkillを自動選択しない。明示的に参照された場合も成果物を変更せず、残留物リスクを指摘と修正案として報告する。

## 最優先契約

- 指摘は検証すべき入力であり、それ自体を新しい要件や成果物にしない。
- 「Aを削除する」を、可能なら「修正後に何が成立するか」という現在形の契約へ翻訳する。
- Aへの言及は、現在の利用者、保守者、実行時契約に固有の価値がある場合だけ残す。
- 必要なテスト、説明、監査証跡まで消す方向へ過剰補正しない。
- ユーザーが依頼した修正範囲を、周辺の一般的な整理や仮想的な懸念へ広げない。

## ワークフロー

### 1. 修正後状態を定義する

レビューの文面をそのまま実装項目へ変換する前に、次を特定する。

- 実際に問題なのは、重複、誤動作、誤解、不要な複雑性、古い説明のどれか。
- 修正後に利用者や後続処理から観測できる状態は何か。
- Aの不在自体が契約なのか、Aは単に現在の実装に不要なのか。
- 指摘は現在の成果物と前提に照らして有効か、また依頼範囲内か。
- 重複が問題なら、詳細を所有する正本と、同義の詳細を持つ他surfaceはどれか。

質問形式の指摘へ機械的に同意しない。成果物を確認し、指摘が正しければ修正する。誤り、重複、範囲外ならその理由を簡潔に示し、不要な変更を加えない。

### 2. 永続物が所有する価値を判定する

新しいテスト、コメント、文書、ガード、設定を残すのは、それが次のいずれかを固有に守る場合だけにする。

- 利用者から観測できる現在の振る舞い、公開契約、不変条件。
- security、privacy、課金、重複副作用、互換性、法令などの重大で現実的な再発リスク。
- 既存の検証では検出できない、起こり得る誤実装。
- 現在のコードや成果物だけでは分からない非自明な理由、制約、運用上の判断。
- 利用者が求めるrelease note、migration history、監査証跡。

どれも所有しない場合は永続物を追加しない。diff、検索、既存テスト、build、render、previewなどの一時的な確認で十分とする。

### 3. 最小の修正へ収束させる

- 不要なAと、Aだけを支えていた分岐、fixture、mock、テスト、コメント、注記、flag、wrapperを除去する。
- 既存テストは、現在も有効な振る舞いを守るなら維持する。古い実装詳細だけを固定している場合は修正または削除する。
- 削除の痕跡として`Aは削除済み`、`Aを追加しないこと`、`以前はAだった`という墓標コメントを置かない。
- Aがないことだけを確認する専用テスト、snapshot、文字列検索を、現在の契約でない限り追加しない。
- 将来のためだけのfallback、互換shim、空wrapper、禁止用flagを作らない。
- 文書やスライドでは、削除した内容を説明する注記、Appendix、speaker noteを、読者価値がない限り追加しない。
- 重複を解消するときは詳細な契約を一つの正本へ統合し、他surfaceから同義の詳細を除く。
  他surfaceには、正本へ到達するroutingと、その層に固有のtrigger metadataや不変条件だけを残す。

### 4. 適切なレベルで検証する

まず既存の関連テスト、validator、build、render、previewで修正後の望ましい状態を確認する。変更した行や削除した名前をそのまま新しいテスト項目にしない。

新しいテストを追加する前に、次をすべて確認する。

1. 現在の公開挙動または重大リスクを固有に守るか。
2. 既存テストでは現実的な再発を検出できないか。
3. 修正前または妥当な誤実装で失敗し、正しい別実装を不必要に拒否しないか。
4. テストを外したときに失う保証を具体的に説明できるか。

重複処理が二重通知、二重課金、二重書き込み、性能劣化などを起こす場合は、その観測可能な結果や`exactly once`契約をテストしてよい。単に同じ内部validationが二箇所に存在しないことは、通常は専用テストにしない。

### 5. 残留物を監査する

変更後のdiffと対象周辺を確認する。

- 指摘された語や構造が、正当な利用箇所以外へ残っていないか。
- 新しいテストやコメントが、修正履歴ではなく現在の契約を説明しているか。
- 既存の有効な保証を弱めたり、テストを通すために期待結果を変えたりしていないか。
- 修正と無関係なscope、抽象化、edge caseを増やしていないか。
- 同じ検証、説明、条件が別の形で再導入されていないか。
- 残したcallerとroutingが正本へ到達し、同義の詳細が他surfaceへ残っていないか。

作業報告では削除したAや判断理由を説明してよい。作業報告は成果物内の恒久コメントやテストとは区別する。

## 判断例

| 状況 | 原則的な扱い |
|---|---|
| 後続で同じvalidationを行うため前段が重複 | 前段を削除し、既存の振る舞いを検証する。専用の不在テストや墓標コメントは追加しない |
| 重複呼び出しが二重課金や二重通知を起こす | 「一度だけ実行される」という観測可能な契約をテストする |
| 古いAPIや危険な依存が禁止されている | 再導入リスクに応じて静的ルール、契約テスト、migration noteを残してよい |
| 文書やスライドから不要な説明を削る | 削除理由の注記を追加せず、残った主経路の理解可能性を確認する |
| コメントが削除済み実装を説明している | コメントも削除する。現在の非自明な理由がある場合だけ、その理由として書き直す |

## 停止条件

- 修正後の望ましい状態が成立している。
- 既存の公開契約と重大リスクへの保証が保たれている。
- reviewで否定された概念を記録するためだけの永続物がない。
- 各新規テスト、コメント、ガード、文書に現在の固有の所有価値がある。
- 依頼外の整理や追加懸念へ作業が広がっていない。

判断が自明なら長い説明を返さず、修正内容と実行した検証だけを報告する。テストやコメントを追加しなかった判断が重要な場合だけ、その理由を簡潔に示す。
