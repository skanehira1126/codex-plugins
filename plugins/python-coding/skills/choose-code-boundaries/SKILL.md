# Choose Code Boundaries

## 原則

抽象化を既定解にしない。変更前の主要処理を入力から出力まで追い、実在する責務境界だけを表現する。

新しい境界は、少なくとも次の1つを所有するときだけ導入する。

- ドメイン上の独立した概念と名前
- 独立して強制すべき契約や不変条件
- 2箇所以上で実際に行われる再利用
- I/O、副作用、外部プロセス、トランザクション、リソース管理
- 独立してテストすべき非自明な処理
- 長い主要処理を明確にする意味のある単位
- 状態、ライフサイクル、共有不変条件、または実際に必要なポリモーフィズム

どれも所有しない場合はインラインを維持する。コードの移動や呼び出しの言い換えを責務分離とみなさず、「将来増えるかもしれない」だけで抽象化しない。

## 判断手順

1. 変更前の処理を読み、入力と出力、変換順序、状態変化、副作用、不変条件、既存の所有者を特定する。
2. インライン、処理内の変数・段階・コメント、関数、class、モジュールを比較し、目的を満たす最も単純な表現を選ぶ。
3. 追加候補ごとに次を確認し、説明できなければ追加しない。
   - 何の責務、契約、不変条件を所有するか。
   - なぜインラインや既存の所有者では不十分か。
   - 削除すると何が失われるか。
   - 読みやすさ、テスト、エラー処理、不変条件の強制を改善するか。単なる委譲や言い換えではないか。
4. 実装後に主要処理とdiffを読み直し、不要な境界を除く。

## 表現ごとのガード

### 関数、helper、wrapper

一度しか使わないことだけで関数化を禁止しない。ただし、独立概念、契約、副作用境界、テスト対象、または主要処理を明確にする意味単位を持たない薄い関数は作らない。

```python
def apply_all(result, items):
    for item in items:
        result = item.apply(result)
    return result
```

このように既存のループを隠すだけならインラインを維持する。入力契約、統一エラー、監査、トランザクションなどを中央で強制する場合は境界になり得るが、先に既存の所有者へ置けないか確認する。

### class、Runner、Manager、Service

状態、ライフサイクル、リソース、共有不変条件、必要なポリモーフィズムのいずれも持たないclassは導入しない。1つの関数を呼ぶだけのRunnerやManager、名前を変えて委譲するだけのServiceを避ける。

### Factory、Registry、Protocol、抽象基底class

複数の実装と共通契約が実在し、設定や外部入力による選択が必要で、直接的な条件分岐より明確になる場合だけ導入する。将来の拡張可能性だけでは導入しない。

### 外部I/O

API呼び出し、再試行、タイムアウト、エラー変換、監査、トランザクションを複数箇所で扱う場合は、これらを強制する副作用境界への抽出を検討する。

## 出力

設計判断が重要な場合だけ簡潔に示す。

```text
選択: インライン / 関数 / class / モジュール
根拠: その境界が所有する責務
却下した案: 過剰だった代替案と理由
```

判断が明白な場合は内部で比較し、実装結果だけを報告する。

## 完了条件

- 主要処理を入力から出力まで追える。
- 各抽象化が契約、不変条件、再利用、副作用境界、テスト対象、意味単位、状態のいずれかを所有する。
- pass-through wrapper、名前だけのclass、将来予測だけのFactoryやRegistryが増えていない。
- 抽象化で読み進めるためのジャンプだけが増えていない。
- 必要な抽象化、検証、エラー処理を削除していない。
