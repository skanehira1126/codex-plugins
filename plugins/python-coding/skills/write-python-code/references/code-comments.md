# コードのコメントとdocstring

今のチャットや差分を知らずに、現在のコードを読む保守者へ向けて書く。コメントを省くと、コードや名前から得られない必要な情報が失われるかを判断する。行数やコメント数だけを削減目標にしない。

## What・How・Why

- What（何をするか）とHow（どう実現するか）は、基本的に名前・型・実装で表す。自明な処理の逐語説明や装飾的な見出し・区切りを加えない。必要ならまず命名や式を明確にするが、コメントを減らすためだけにhelperやclassへ分割しない。
- コメントにはコードから読み取れないWhy（なぜこの実装が必要か）、外部制約、不変条件を残す。非自明なアルゴリズムのHowや、長い処理の意味のある段階を示す説明も、理解を助ける場合は簡潔に書く。

## 現在も必要な理由を残す

チャットの経緯、ユーザーやレビューへの返答、変更前後の実況をコメントに残さない。変更履歴はGitやPRへ置く。過去の不具合や外部仕様が現在の制約を説明する場合は、短い技術的理由と必要な参照を残す。会話やリンク先を読まないと理由が全く分からない書き方は避ける。

```python
# 避ける: レビューで指摘されたので、リストから辞書に変更した。
# 残す: 同一IDの再送で二重計上しないよう、ID単位で保持する。
```

Whyを書くために、性能・安全性・互換性・業務上の理由を推測で補わない。コード、テスト、仕様、確認された要件で裏付けられる理由だけを書く。上の例も、再送と二重計上防止が実際の要件である場合に限る。

## docstringとテスト

- docstringは利用者が呼び出すために必要なWhatと契約を説明する。非自明な入力条件、単位、副作用、例外などを含め、名前・型の反復、実装手順の実況、内容のない定型セクションは加えない。
- テスト名・parameter ID・assertで分かる期待結果をコメントやdocstringで繰り返さない。入力やfixtureの選択、回帰を起こす条件、期待値の根拠が非自明なら補足する。期待値の説明をテスト対象の計算のコピーで代用しない。
- Arrange／Act／Assertなどの段階ラベルは機械的に付けず、非自明な段階を区別する価値とプロジェクト規約で判断する。

## 変更範囲

変更によって古くなった説明は更新・削除するが、無関係なコメント整理へ広げない。コメントだけの整理を、設計変更やテストケース・assertの削減へ広げない。公開APIの文書契約、プロジェクト指定の書式、ライセンス表記、型検査・lintなどの機械向け指示を保持する。

## 参考資料

判断要素の出典。通常の適用でリンク先を読み込む必要はない。

- [Self-explanatory Code Commenting](https://github.com/github/awesome-copilot/blob/main/instructions/self-explanatory-code-commenting.instructions.md): 自明な説明と変更履歴を避ける。
- [Lean Comments](https://github.com/github/awesome-copilot/blob/main/skills/lean-comments/SKILL.md): 将来の保守者を想定し、コメントの必要性と理由の根拠を判断する。
- [Google Python Style Guide](https://google.github.io/styleguide/pyguide.html#s3.8-comments-and-docstrings): 呼び出し側の文書と実装コメントを区別し、テスト名の反復を避ける。
