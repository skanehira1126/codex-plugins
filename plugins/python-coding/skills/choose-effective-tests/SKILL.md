# Choose Effective Tests

## 原則

テスト数やcoverageを成果にせず、変更された公開挙動と主要リスクを守る最小のテスト集合を選ぶ。

候補テストは、次の少なくとも1つを固有に所有するときだけ追加する。

- 公開契約、不変条件、または利用者から観測できる振る舞い
- 意味の異なる同値クラス、境界、失敗モード、状態遷移
- 実際のバグに対する回帰防止
- unit testでは守れない統合境界、設定、実依存との契約
- 既存テストが検出しない現実的な欠陥

どれも所有しない場合は追加しない。テスト件数、重複コード、同じ行を通ることだけで既存テストを過剰と判断せず、独立した契約、障害の局所化、所有境界を守る価値も確認する。

## 判断手順

1. リポジトリのテスト方針、既存fixture、命名、テストレイヤー、対象周辺のテストを読む。
2. 変更前後で変わる公開挙動と、守るべき主要リスクを列挙する。実装の行や分岐をそのままテスト項目へ変換しない。
3. 既存テストが守る振る舞い、入力クラス、oracle、レイヤーを確認する。
4. 候補ごとに次を確認し、説明できなければ既存テストの改善、統合、または追加なしを選ぶ。
   - どの公開契約またはリスクを固有に守るか。
   - 既存テストとGiven、When、Then、oracleのどこが異なるか。
   - 修正前コードや現実的な誤実装で失敗するか。
   - より低コストで同じ検出力を得られないか。
5. 実装後に新規テストを1件ずつ外した場合に失う保証を考え、失うものを説明できないテストを残さない。

既存テストの無関係な整理や削除まで作業を広げない。対象変更と重なる低価値テストを変更する必要がある場合だけ扱う。

## テストケースの選び方

### 同値クラスと境界

仕様上の同値クラス、不連続点、例外条件から代表値を選ぶ。値を思いつく限り列挙せず、同じ振る舞いとoracleを持つ値違いは`pytest.mark.parametrize`への統合を検討する。

異なる失敗理由や状態遷移を、見た目が似ているだけで1つにまとめない。parameterの直積は、組み合わせ固有の相互作用がある場合だけ作る。

一般化できる公開不変条件が明確な場合はproperty-based testingを検討する。仕様から導けないpropertyや、少数の代表例で十分な処理へ反射的に導入しない。

### 観測可能な振る舞い

戻り値、公開状態、永続化結果、外部へ公開された副作用を検証する。private helper、中間表現、内部呼び出し順、call countは、それ自体がプロトコル上の契約でない限り固定しない。

辞書やobject全体の厳密比較で無関係なfieldまで固定せず、契約に必要な結果をassertする。例外messageの完全一致も、文言が公開契約の場合だけ使う。

### Mockとfixture

外部I/O、時刻、乱数、非決定的処理、高コストな依存など、制御が必要な境界だけmockする。可能なら観測可能な状態、fake、または小さな統合テストを優先する。

stubした値がそのまま返ることだけをassertしない。mockの呼び出し詳細は、呼び出し自体が契約である場合だけ検証する。大きな共通fixtureや遠い`autouse` fixtureで、各テストに不要な状態を持ち込まない。

### 読みやすさ

テストは失敗時に壊れた振る舞いを特定できる単位にする。テストコードの多少の重複は、意図をその場で読めるなら許容する。短くするためだけにhelperやfixtureへ隠し、テストの因果関係を追いにくくしない。

## 検証

- バグ修正では、可能なら新規・変更テストが修正前コードで失敗することを確認する。
- coverageは未実行領域を探す補助に使い、100%達成だけを目的にテストを追加しない。
- fault detectionが不明な重要ロジックでは、既存設定がある場合や費用が妥当な場合に限り、対象を絞ったmutation testingを検討する。
- プロジェクト標準のテストを実行し、必要に応じて遅いテスト、flaky、共有状態への依存を確認する。
- full suiteやmutation testingが高コストなら、変更対象のテストを先に実行し、未実行範囲を完了報告に明記する。

## 停止条件

次を満たしたら、追加できるedge caseを探し続けず停止する。

- 変更された公開挙動と主要リスクがテストへ対応している。
- 各新規テストが既存テストとは異なる保証を持つ。
- 主要な正常系、意味の異なる境界・失敗系、必要な状態遷移を扱っている。
- 実装詳細だけを固定するassertや不要なmockがない。
- 追加候補に固有の契約、リスク、または欠陥検出上の役割が残っていない。

## 出力

テスト選択の判断が重要な場合だけ簡潔に示す。

```text
守る挙動・リスク: <公開契約または回帰>
追加・変更したテスト: <固有の役割>
追加しなかった候補: <既存テストとの重複または低い限界価値>
検証: <修正前失敗、実行したtest、coverage・mutationなど>
```

判断が明白な場合は内部で比較し、実装結果と検証だけを報告する。

## 完了条件

- 各新規テストが守る公開挙動またはリスクを説明できる。
- 同じGiven、When、Then、oracleのテストを重ねていない。
- テストがprivate実装ではなく利用者から観測できる結果を優先している。
- coverageや件数のためだけのテスト、tautological assertion、不要なmockが増えていない。
- 必要な回帰、統合契約、重要な失敗系を削減していない。
- 実行した検証と未検証事項を報告している。
