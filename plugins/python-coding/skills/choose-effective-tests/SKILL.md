# Choose Effective Tests

単独で呼び出された場合は、未読の[共通Skill](../write-python-code/SKILL.md)を先に読む。同じ作業で既読なら再読せず、以下を適用する。

## 原則

テスト数やcoverageを成果にせず、変更された公開挙動と主要リスクを守る最小のテスト集合を選ぶ。

候補テストは、次の少なくとも1つを固有に所有するときだけ追加する。

- 公開契約、不変条件、または利用者から観測できる振る舞い
- 意味の異なる同値クラス、境界、失敗モード、状態遷移
- 実際のバグに対する回帰防止
- unit testでは守れない統合境界、設定、実依存との契約
- 既存テストが検出しない現実的な欠陥

どれも所有しない場合は追加しない。テスト件数、重複コード、同じ行を通ることだけで既存テストを過剰と判断せず、独立した契約、障害の局所化、所有境界を守る価値も確認する。

## 判断手順

1. リポジトリのテスト方針、既存fixture、命名、テストレイヤー、対象周辺のテストを読む。
2. 依頼、仕様、呼び出し元の使い方から、今回守る挙動とその根拠を短く整理する。複数の関数が一緒に一つの結果を保証するなら、一件にまとめる。
3. 代表的な入力と操作を一つ取り、利用者から見える期待結果を書く。どんな誤りで落ち、どんな正当な変更なら通るべきかを当てて、保証に不要な入力・設定・依存を外す。
4. **その入力を受け付けた後、何が起きると約束しているか**で進め方を決める。
   - **期待結果を新たに決める場合は、編集前に相談する。** たとえば「引数を省略できるように」は呼び方の指定で、省略時の結果は別の判断になる。その結果まで依頼や既存の契約で定まっているかを確認する。根拠が定数名や他の経路からの推測だけなら、代表例に推奨案と理由を添えて質問し、回答を待つ。依頼に「未決」と書かれていなくても同じ。
   - **期待結果が明確な小さな回帰修正は、セルフレビューで進める。** 指定された例や既存の契約に照らして不具合を再現する。
5. 既存テストの入力、操作、期待結果とその判定方法、テストレイヤーを照合する。同じ保証があれば追加せず、不足があれば既存テストの改善・統合・新規追加から、必要な検出力を得られる最も低コストな方法を選ぶ。設定と実依存の組み合わせ自体が保証なら、その組み合わせを通る統合テストで確かめる。
6. 「設定に従う」ことが保証なら、テストで設定値を与え、その値に応じた結果を公開経路から確かめる。現在の既定値そのものを期待値に固定するのは、その値まで保証するときに限る。変更してよい設定値を別の値に替えてもテストが通るか確かめる。
7. 実装後に新規テストを1件ずつ外した場合に失う保証を考え、失うものを説明できないテストを残さない。

既存テストの無関係な整理や削除まで作業を広げない。対象変更と重なる低価値テストを変更する必要がある場合だけ扱う。

## テストケースの選び方

### 同値クラスと境界

仕様上の同値クラス、不連続点、例外条件から代表値を選ぶ。値を思いつく限り列挙せず、同じ振る舞いとoracleを持つ値違いは`pytest.mark.parametrize`への統合を検討する。

異なる失敗理由や状態遷移を、見た目が似ているだけで1つにまとめない。parameterの直積は、組み合わせ固有の相互作用がある場合だけ作る。

一般化できる公開不変条件が明確な場合はproperty-based testingを検討する。仕様から導けないpropertyや、少数の代表例で十分な処理へ反射的に導入しない。

### 観測可能な振る舞い

戻り値、公開状態、永続化結果、外部へ公開された副作用を既定の検証対象にする。privateな
処理でも、stableなseam、固有の非自明なrisk、高コストな公開経路、障害を局所化する価値が
ある場合は直接testしてよい。中間表現、内部呼び出し順、call countは、それ自体が
プロトコル上の契約でない限り固定しない。

辞書やobject全体の厳密比較で無関係なfieldまで固定せず、契約に必要な結果をassertする。例外messageの完全一致も、文言が公開契約の場合だけ使う。

### Mockとfixture

外部I/O、時刻、乱数、非決定的処理、高コストな依存など、制御が必要な境界だけmockする。可能なら観測可能な状態、fake、または小さな統合テストを優先する。

stubした値がそのまま返ることだけをassertしない。mockの呼び出し詳細は、呼び出し自体が契約である場合だけ検証する。大きな共通fixtureや遠い`autouse` fixtureで、各テストに不要な状態を持ち込まない。

### 読みやすさ

テストは失敗時に壊れた振る舞いを特定できる単位にする。テストコードの多少の重複は、意図をその場で読めるなら許容する。短くするためだけにhelperやfixtureへ隠し、テストの因果関係を追いにくくしない。

## 検証

- バグ修正では、可能なら新規・変更テストが修正前コードで失敗することを確認する。
- coverageは未実行領域を探す補助に使い、100%達成だけを目的にテストを追加しない。
- fault detectionが不明な重要ロジックでは、既存設定がある場合や費用が妥当な場合に限り、対象を絞ったmutation testingを検討する。
- 変更対象のテストから始め、projectの必須checkと、統合境界・共有状態など対象変更に関わる検証を完了する。追加・再実行は、新たな変更、失敗、未解決の懸念に応じて行う。
- 必要なfull suiteやmutation testingなどを実行できない場合は、未検証範囲、理由、影響を完了報告に明記する。

## 停止・完了条件

次を満たしたら、追加できるedge caseを探し続けず停止する。

- 変更された公開挙動と主要リスクがテストへ対応している。
- 各新規テストが「原則」と「判断手順」の選択基準を満たす。
- 対象変更に関係する正常系、意味の異なる境界・失敗系、必要な状態遷移を扱っている。
- 「テストケースの選び方」に沿い、同じGiven、When、Then、oracleの重複や、tautological assertionがない。
- 必要な回帰、統合契約、重要な失敗系を削減していない。
- 実行した検証と未検証事項を報告している。

## 出力

テスト選択の判断が重要な場合だけ簡潔に示す。

```text
守る挙動・リスク: <公開契約または回帰>
追加・変更したテスト: <固有の役割>
追加しなかった候補: <既存テストとの重複または低い限界価値>
検証: <修正前失敗、実行したtest、coverage・mutationなど>
```

判断が明白な場合は、完了報告には実装結果と検証だけを記す。
