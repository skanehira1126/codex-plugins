# テキスト文書アーキテクト

文章中心の業務文書を、初見の読者が書き手の論理や利用手順を復元せずに、走査し、
連続して読み、または必要な情報を引き当てられる形に設計する。情報を均一な密度で
並べず、文書の読み方に合う論理、認知動作、ナビゲーションを作る。

適用可否は**入力元ではなく、最終成果物**で判断する。入力がPowerPointでも出力がWord、Google Docs、Markdownなど文章中心ならこのSkillを使う。出力がスライドなら、入力が報告書であってもこのSkillを使わない。

## 最優先契約：読者の主経路と指定された成果物を守る

- 本文は、対象読者が目的を達成するための最短かつ十分な読解経路にする。
- 詳細をすべて本文へ押し込まず、表・コールアウト、脚注・注記、Appendix、削除へ振り分ける。
- 結論、解釈、作業結果を変え得る制約、リスク、前提、証拠不足をAppendixへ隠さない。
- ユーザーが指定した形式を守り、依頼されていない別形式を納品条件にしない。
- 既存文書の改訂では、見出しスタイル、表、図、引用、脚注、コメント、変更履歴、リンク、編集可能な構造を可能な限り保つ。
- 根拠、引用、数値、出典、組織固有の事情を捏造しない。

この契約に違反する成果物は、文章が滑らかでも未完成とみなす。

## 基本モデル

連続して読む文書では、文書を読者状態の遷移として扱う。

```text
読者の状態A
  → 状況と全体像をつかむ
  → 問い・違和感・判断すべき対立を持つ
  → 根拠・事例・具体的な現象を観察する
  → 原因・仕組み・概念を理解する
  → 初期認識を更新する
  → 選択肢や不確実性を評価する
  → 判断・行動・適用へ進む
  → 新しい理解を全体へ統合する
読者の状態B
```

検索・引き当てを主目的とする文書では、状態遷移ではなく次の利用経路を設計する。

```text
利用者の作業
  → 適用範囲と全体マップ
  → 規則または手順
  → 条件分岐と例外
  → 結果、失敗時の扱い、関連参照
```

文書種別によって順序は変わる。連続読解では論理の連続性と認知動作、検索・引き当て
では予測可能な入口、分岐、参照を優先する。文の長短、修辞疑問、ためらいで表面的な
リズムを作らない。

## 構造profile

動作モードとは別に、`references/text-patterns.md`を読み、主な読み方をprimary profileと
して選ぶ。利用者の仕事が複数ある場合は、secondary profileのaccess pathを必要な章や
付属部分へ追加してよい。

- **sequential**：意思決定、提案、分析、進捗など、順に読むことで判断や理解へ進む文書。
- **learning**：具体例、概念、適用を往復しながらモデルを獲得する解説・学習文書。
- **lookup/reference**：必要な規則、手順、条件、例外を検索・引き当てする業務手順書、規程、仕様書、参照文書。

lookup/referenceへreader-state narrative、中心的な対立、結論型見出しを強制しない。
sequentialやlearningを、検索性だけを優先した項目集へ変えない。

## 動作モード

依頼内容から次のモードを推定する。

- **設計（design）**：文書設計書、profileに合うcontent mapと構造アウトライン、情報配置、品質ゲート結果を作る。
- **作成（create）**：設計を行った後、ハードゲート違反を修正し、完全な草稿または指定形式の成果物を作る。
- **レビュー（review）**：既存文書を診断・報告し、文書や関連ファイルを変更しない。
- **改訂（revise）**：診断後、妥当な事実・引用・書式・編集可能な構造を保ち、ハードゲート違反を修正する。

「報告書を書いて」のように文章中心の成果物が明らかな依頼は**作成モード**とし、設計ゲートから本文作成・検証まで進む。設計承認を待つのは、そのcheckpointをユーザーが求めた場合に限る。「資料を作って」のように文章文書かスライドかで成果物が変わる依頼は、会話と素材から最終形式を特定する。安全に推定できない場合だけ、最終形式を一つ確認してからこのSkillまたは`presentation-architect`へ振り分ける。

**改訂**で自己レビューまたは外部レビューの指摘を反映するときは、利用可能なら
`revision-hygiene:revision-hygiene`も使い、どの検証や説明を成果物へ残すべきか判断する。
文章構造と文書品質については引き続きこのSkillを優先する。

# 標準ワークフロー

## 1. 素材、制約、実際の成果物を確認する

本文を書く前に、提供された素材を読む。次を特定または合理的に推定する。

- 最終形式、期待される長さ、利用日・締切
- 主な読者、前提知識、態度、利害、反論、意思決定権限
- 読み方：連続読解、役員向け事前配布、分析評価、学習、業務参照、検索・引き当て
- lookup/referenceで代表利用者が検索する作業、規則、例外、失敗時の情報
- 必須の事実、データ、引用、出典、テンプレート、用語
- 何を編集可能な状態で残すか、最終成果物をどう検証するか

既存ファイルの改訂では、断片的な抜粋だけでなく実際の成果物を確認する。外部・時点依存の主張は利用可能な調査手段で検証する。

## 2. 重要な意思決定を解消し、テキスト文書設計書を作る

設計・作成モードでは、不足を調査できる事実、安全な既定値、ユーザーが決める重要事項に分ける。事実は調べ、既定値は明示して進み、成果物を大きく変えて安全に補えない事項だけ確認する。

壁打ちを明示された場合は、`../../references/authoring-interview.md`を読み、重要な未決定事項を
解消してから依頼されたモードへ進む。

`assets/text-document-brief.md`を使い、次を設定する。

- sequential/learningでは読者の状態AとB、lookup/referenceでは代表的な検索作業と到達結果
- 文書が可能にする理解、判断、意思決定、行動
- 中心命題または支配的な目的を一つ
- 読み方の契約とナビゲーションモデル
- 目的に必要十分な主要主張、学習単位、または規則・手順群と、その根拠、例、例外、含意
- 文体、長さ、非目的、前提、証拠不足

主張を扱う場合は**事実・解釈・仮説・提案**に分類する。調査、提供ファイル、数値を
使う場合は`references/evidence-and-sources.md`を読む。

## 3. 読者の仕事に合う文書パターンを選ぶ

primary profileの中で、固定テンプレートではなく読者が文書を使って何をするかに合う
patternを選ぶ。secondary profileがある場合は、その利用作業に必要な入口と構造だけを
追加する。

- 意思決定メモ・役員向け事前配布
- 提案書・推奨書
- 分析・調査報告書
- 解説記事・学習資料
- 業務手順書・規程・仕様書・参照文書
- 進捗報告

「背景 → 課題 → 施策 → まとめ」を機械的に使わない。

## 4. profileに合うcontent mapを作る

選択したprofileに合う関係を整理する。

```text
sequential: 主張・状況 → 根拠 → 推論 → 含意 → 但し書き・反論
learning: 具体的な問い → 事例 → 概念・仕組み → 適用 → 誤解・限界 → 次の利用
lookup/reference: 利用作業 → 適用範囲・入力 → 規則・手順 → 分岐・例外 → 結果・復旧・関連参照
```

支配的な目的を支えず、必要な前提を与えず、依頼された判断・学習・作業を可能にせず、
参照価値もない情報は削除候補とする。

項目一覧だけで済ませず、profileに必要な優先順位、因果、順序、比較、依存関係、分岐、
例外を明示する。

## 5. 構造アウトラインを作る

`assets/reader-motion-outline.md`を使う。sequential/learningでは各主要セクションについて
次を定義する。

- 読者がその章で持つ問い
- メッセージまたは検索手掛かりを持つ見出し
- 主な認知動作：**状況把握、問い、観察、説明、再解釈、評価、判断、行動、統合**
- 根拠、事例、定義
- 抽象度：具体、混在、抽象
- なぜ次の章が続くのか

全文を書く前に、次の二つのゲートを通す。

### 見出しだけで読むゲート

1. 文書タイトルと見出しだけを読む。
2. 中心命題または支配的な目的と、論理の進行または検索経路が理解できるか確認する。
3. 文書種別が許す場合、「背景」「課題」「考察」「まとめ」のような汎用ラベルを、結論・問い・対比・作業・具体的な参照ラベルへ書き換える。
4. 章間の接続や検索経路に、読者が補わなければならない因果、前提、適用条件がないか確認する。

### 読者動作ゲート

`references/cognitive-rhythm.md`を読み、文書種別に応じた読者動作、抽象度、問い、
ナビゲーションの流れを確認する。

lookup/referenceでは読者動作ゲートの代わりにnavigation gateを行う。代表的な利用作業から
入り、適用範囲、規則または手順、条件分岐、例外、失敗時の扱い、関連参照へ、文書を
順読せず到達できるか確認する。

## 6. 本文を書く前に情報を配置する

`references/content-placement.md`を使い、各候補情報を本文、表／コールアウト、
脚注／注記、Appendix、削除のいずれかへ配置する。詳細な配置判断は同referenceを
正本とする。

## 7. 必要な観点を分けて確認する

骨格と接続、根拠と確度、認知動作または検索経路、重複と不要な実況を、それぞれ
確認する。短い文書では一度に扱ってよく、長文や複雑な参照文書では観点を分ける。

推論には段落を使う。箇条書きは本当に並列な項目に使う。項目間の関係が重要な場合は、列挙の後に優先順位、因果、結果、前の事例との接続を明示する。

## 8. 認知的なメリハリを確認する

sequential/learningでは`references/cognitive-rhythm.md`を使い、章ごとの認知動作、
抽象度、密度、問い、確信度、案内文を監査する。変化は意味と根拠に基づかせ、関係を
示さない文章の実況は削除する。lookup/referenceでは、見出し、用語、cross-reference、
分岐、例外の一貫性と引き当てやすさを監査する。

## 9. 初見読者・信頼性の確認を行う

指定した対象読者が前提を自力で補わずに使えるか確認し、次を修正する。公開文書、
onboarding、または対象読者が不明な場合だけ、より低文脈の読者でも確認する。

- 未定義の用語・略語
- 必要なメンタルモデルの欠落
- 隠れた因果・優先順位
- 参照先が曖昧な指示語
- 主張から離れすぎた根拠
- 定義、範囲、期間、分母、出典がない数値
- 事実・解釈・仮説・提案が同じ確度で書かれている箇所

`references/quality-rubric.md`で文書を採点する。

## 10. 成果物を生成・検証する

`references/artifact-production.md`を読む。`documents`など形式固有のSkillが利用可能な場合は、テンプレート処理、ファイル生成、レンダリング、成果物QAにそのSkillを使う。このSkillは、支配的な目的、profile別content map、構造アウトライン、情報配置、根拠の扱いを統制する。指示が競合する場合は、ユーザーが指定した成果物形式と、形式固有Skillの技術的な生成・検証要件を守る。既存の豊かな成果物を、単純なプレーンテキストへ置き換えない。

同referenceと形式固有Skillの生成・QA手順に従い、指定形式に必要なrenderまたはpreviewを
行ってから納品する。

## 11. 独立した編集者としてレビュー・改訂する

書き手の視点を離れ、`references/quality-rubric.md`のハードゲートを懐疑的な編集者として
確認し、選択した動作モードの契約に従って違反を処理する。

Markdownのアウトラインまたは草稿がある場合は、必要に応じて次を実行する。

```bash
python scripts/lint_text_document.py path/to/document.md --mode sequential --check-sources
```

lookup/referenceでは`--mode reference`、意思決定文書では`--mode decision`を使う。

日本語の別名も使える。

```bash
python scripts/lint_text_document.py path/to/document.md --モード 連続読解 --出典確認
```

lintは編集上の注意箇所を示すものであり、品質や事実性を自動証明するものではない。

# 出力契約

## 設計モード

次を返す。

1. テキスト文書設計書
2. 読者の状態変化または代表的な検索作業と、中心命題または支配的目的
3. primary profileのcontent mapと、必要なsecondary access path
4. 読者動作アウトラインまたはnavigation map
5. 本文・表／コールアウト・注記・Appendix・削除の配置
6. 前提と証拠不足
7. 品質ゲート結果

依頼されていない限り、完全な本文は書かない。

## 作成モード

完全な草稿または指定形式の成果物を納品する。重要な前提、未解決の証拠不足、検証上のリスクだけを簡潔に示す。求められない限り、長い作業ログは出さない。

## レビューモード

優先度順に指摘する。各指摘について、位置、読者への影響、構造上の原因、具体的な
修正案を示す。全体構造が弱い場合は、profileに合う修正版の見出しマップと読者動作または
navigation mapも示す。

構造化されたreview artifactが有用な場合は`assets/review-report.md`を使う。

## 改訂モード

修正版の成果物と簡潔な変更概要を納品する。妥当な事実、引用、出典、スタイル、コメント、編集可能な構造を保つ。
