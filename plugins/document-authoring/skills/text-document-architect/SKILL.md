# テキスト文書アーキテクト

文章中心の業務文書を、初見の読者が書き手の論理を復元せずに、走査し、連続して読み、理解し、必要な箇所へ戻れる形に設計する。情報を均一な密度で並べるのではなく、論理の連続性を保ちながら、読者の認知動作に意図的なメリハリを作る。

適用可否は**入力元ではなく、最終成果物**で判断する。入力がPowerPointでも出力がWord、Google Docs、Markdownなど文章中心ならこのSkillを使う。出力がスライドなら、入力が報告書であってもこのSkillを使わない。

## 最優先契約：読者の主経路と編集可能な原本を守る

- 本文は、対象読者が目的を達成するための最短かつ十分な読解経路にする。
- 詳細をすべて本文へ押し込まず、表・コールアウト、脚注・注記、Appendix、削除へ振り分ける。
- 結論を変え得る制約、リスク、前提、証拠不足をAppendixへ隠さない。
- ユーザーがPDFのみを明示的に求めない限り、Word等では編集可能な原本を維持する。
- 既存文書の改訂では、見出しスタイル、表、図、引用、脚注、コメント、変更履歴、リンク、編集可能な構造を可能な限り保つ。
- PDFや画像レンダリングは品質確認・配布のために使い、編集可能な原本の代替にしない。
- 根拠、引用、数値、出典、組織固有の事情を捏造しない。

この契約に違反する成果物は、文章が滑らかでも未完成とみなす。

## 基本モデル

文書を、読者状態の遷移として扱う。

```text
読者の状態A
  → 状況と全体像をつかむ
  → 問い・違和感・判断すべき対立を持つ
  → 根拠・事例・具体的な現象を観察する
  → 原因・仕組み・概念を理解する
  → 初期認識を更新する
  → 選択肢や不確実性を評価する
  → 判断・行動・適用へ進む
  → 新しい理解を全体へ統合する
読者の状態B
```

文書種別によって順序は変わる。必須なのは、**論理の連続性を壊さず、読者に求める認知動作を意図的に変化させること**である。文の長短を無作為に変えたり、修辞疑問やためらいを挿入したりして、表面的なリズムを作らない。

## 動作モード

依頼内容から次のモードを推定する。

- **設計（design）**：文書設計書、論証・根拠マップ、読者動作アウトライン、情報配置、品質ゲート結果を作る。
- **作成（create）**：設計を行った後、ハードゲート違反を修正し、完全な草稿または指定形式の成果物を作る。
- **レビュー（review）**：既存文書を診断・報告し、文書や関連ファイルを変更しない。
- **改訂（revise）**：診断後、妥当な事実・引用・書式・編集可能な構造を保ち、ハードゲート違反を修正する。

「報告書を書いて」のように文章中心の成果物が明らかな依頼は**作成モード**とし、全文を書く前に設計ゲートを通す。「資料を作って」のように文章文書かスライドかで成果物が変わる依頼は、会話と素材から最終形式を特定する。安全に推定できない場合だけ、最終形式を一つ確認してからこのSkillまたは`presentation-architect`へ振り分ける。

**改訂**で自己レビューまたは外部レビューの指摘を反映するときは、利用可能なら`revision-hygiene`も使い、どの検証や説明を成果物へ残すべきか判断する。文章構造と文書品質については引き続きこのSkillを優先する。

# 標準ワークフロー

## 1. 素材、制約、実際の成果物を確認する

本文を書く前に、提供された素材を読む。次を特定または合理的に推定する。

- 最終形式、期待される長さ、利用日・締切
- 主な読者、前提知識、態度、利害、反論、意思決定権限
- 読み方：連続読解、役員向け事前配布、分析評価、学習、業務参照、検索・引き当て
- 必須の事実、データ、引用、出典、テンプレート、用語
- 何を編集可能な状態で残すか、最終成果物をどう検証するか

既存ファイルの改訂では、断片的な抜粋だけでなく実際の成果物を確認する。外部・時点依存の主張は利用可能な調査手段で検証する。

## 2. 重要な意思決定を解消し、テキスト文書設計書を作る

設計・作成モードでは、不足を調査できる事実、安全な既定値、ユーザーが決める重要事項に分ける。事実は調べ、既定値は明示して進み、成果物を大きく変えて安全に補えない事項だけ確認する。

壁打ちを明示された場合は、前提が決まった重要な質問から最大3件ずつ、推奨案と短い理由を添えて聞く。回答に依存する質問は後へ回し、重要な未決定事項がなくなったら合意内容を要約して依頼されたモードへ進む。文体や粒度を言葉だけで選べない場合は、必要に応じて短い会話内サンプルを示す。reviewモードにはこの手順を適用しない。

`assets/text-document-brief.md`を使い、次を設定する。

- 読者の状態Aと、到達させたい状態B
- 文書が可能にする理解、判断、意思決定、行動
- 中心命題または支配的な目的を一つ
- 読み方の契約とナビゲーションモデル
- 中心命題を支える2〜5個の主要主張、根拠、反論、含意
- 文体、長さ、非目的、前提、証拠不足

主張は**事実・解釈・仮説・提案**に分類する。調査、提供ファイル、数値を使う場合は`references/evidence-and-sources.md`を読む。

## 3. 読者の仕事に合う文書パターンを選ぶ

`references/text-patterns.md`を参照し、固定テンプレートではなく、読者が文書を使って何をするかで構成を選ぶ。

- 意思決定メモ・役員向け事前配布
- 提案書・推奨書
- 分析・調査報告書
- 解説記事・学習資料
- 業務手順書・規程・仕様書・参照文書
- 進捗報告

「背景 → 課題 → 施策 → まとめ」を機械的に使わない。

## 4. 論証・根拠マップを作る

主要主張ごとに次を整理する。

```text
主張 → 根拠 → 推論 → 含意
             → 但し書き・反論・代替説明
```

中心命題を支えず、必要な前提を与えず、反論を解消せず、依頼された行動を可能にせず、参照価値もない情報は削除候補とする。

論点一覧は論証ではない。優先順位、因果、順序、比較、依存関係を明示する。

## 5. 読者動作アウトラインを作る

`assets/reader-motion-outline.md`を使い、各主要セクションについて次を定義する。

- 読者がその章で持つ問い
- メッセージまたは検索手掛かりを持つ見出し
- 主な認知動作：**状況把握、問い、観察、説明、再解釈、評価、判断、行動、統合**
- 根拠、事例、定義
- 抽象度：具体、混在、抽象
- なぜ次の章が続くのか

全文を書く前に、次の二つのゲートを通す。

### 見出しだけで読むゲート

1. 文書タイトルと見出しだけを読む。
2. 目的、中心命題、論理の進行が理解できるか確認する。
3. 文書種別が許す場合、「背景」「課題」「考察」「まとめ」のような汎用ラベルを、結論・問い・対比・作業・具体的な参照ラベルへ書き換える。
4. 章間の接続に、読者が補わなければならない因果や前提がないか確認する。

### 読者動作ゲート

`references/cognitive-rhythm.md`を読み、文書種別に応じた読者動作、抽象度、問い、
ナビゲーションの流れを確認する。

## 6. 本文を書く前に情報を配置する

`references/content-placement.md`を使い、各候補情報を本文、表／コールアウト、
脚注／注記、Appendix、削除のいずれかへ配置する。詳細な配置判断は同referenceを
正本とする。

## 7. 段階的に執筆する

長文本文を、一度の均一な生成で書き切らない。

1. **骨格パス**：見出し、章の問い、トピックセンテンス
2. **推論パス**：段落単位の論理、因果、接続
3. **根拠パス**：データ、事例、引用、出典、但し書き、確度
4. **メリハリ・パス**：認知動作と抽象度の変化、均一な密度の修正
5. **圧縮パス**：重複、文章の実況、理解や行動を変えない詳細の削除

推論には段落を使う。箇条書きは本当に並列な項目に使う。項目間の関係が重要な場合は、列挙の後に優先順位、因果、結果、前の事例との接続を明示する。

## 8. 認知的なメリハリを確認する

`references/cognitive-rhythm.md`を使い、章ごとの認知動作、抽象度、密度、問い、
確信度、案内文を監査する。変化は意味と根拠に基づかせ、関係を示さない文章の実況は
削除する。

## 9. 初見読者・信頼性の確認を行う

対象読者より前提知識が一段少ないテスト読者を想定し、次を修正する。

- 未定義の用語・略語
- 必要なメンタルモデルの欠落
- 隠れた因果・優先順位
- 参照先が曖昧な指示語
- 主張から離れすぎた根拠
- 定義、範囲、期間、分母、出典がない数値
- 事実・解釈・仮説・提案が同じ確度で書かれている箇所

`references/quality-rubric.md`で文書を採点する。

## 10. 成果物を生成・検証する

`references/artifact-production.md`を読む。`documents`など形式固有のSkillが利用可能な場合は、テンプレート処理、ファイル生成、レンダリング、成果物QAにそのSkillを使う。このSkillは、中心命題、論証、読者動作、情報配置、根拠の扱いを統制する。指示が競合する場合は、ユーザーが指定した成果物形式と、形式固有Skillの技術的な生成・検証要件を守る。既存の豊かな成果物を、単純なプレーンテキストへ置き換えない。

同referenceの生成・QA手順に従い、最終成果物をレンダリングまたはプレビューしてから
納品する。

## 11. 独立した編集者としてレビュー・改訂する

書き手の視点を離れ、`references/quality-rubric.md`のハードゲートを懐疑的な編集者として
確認し、選択した動作モードの契約に従って違反を処理する。

Markdownのアウトラインまたは草稿がある場合は、必要に応じて次を実行する。

```bash
python scripts/lint_text_document.py path/to/document.md --mode sequential --check-sources
```

日本語の別名も使える。

```bash
python scripts/lint_text_document.py path/to/document.md --モード 連続読解 --出典確認
```

lintは編集上の注意箇所を示すものであり、品質や事実性を自動証明するものではない。

# 出力契約

## 設計モード

次を返す。

1. テキスト文書設計書
2. 読者の状態変化と中心命題
3. 論証・根拠マップ
4. 読者動作アウトライン
5. 本文・表／コールアウト・注記・Appendix・削除の配置
6. 前提と証拠不足
7. 品質ゲート結果

依頼されていない限り、完全な本文は書かない。

## 作成モード

完全な草稿または指定形式の成果物を納品する。重要な前提、未解決の証拠不足、検証上のリスクだけを簡潔に示す。求められない限り、長い作業ログは出さない。

## レビューモード

優先度順に指摘する。各指摘について、位置、読者への影響、構造上の原因、具体的な修正案を示す。全体構造が弱い場合は、修正版の見出しマップと読者動作の並びも示す。

## 改訂モード

修正版の成果物と簡潔な変更概要を納品する。妥当な事実、引用、出典、スタイル、コメント、編集可能な構造を保つ。
