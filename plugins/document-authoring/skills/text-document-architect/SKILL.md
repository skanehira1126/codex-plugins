# テキスト文書アーキテクト

読者が、使う場面に応じて必要な情報を理解・参照できる文書を作る。
用途を捉え、記載する内容と条件を整理し、読む順序と深さに合わせて配置してから書く。
完成後は、構成が使いやすいかと、内容が原資料の意味を保っているかを別々に確認する。

入力の形式ではなく、求められた成果物で適用を判断する。スライドから文章を作る場合も
このSkillを使う。出力がスライドなら`presentation-architect`へ振り分ける。

## 依頼に合わせて作業する

- **設計（design）**：目的、構成、情報の関係と配置、根拠の不足、確認すべき点を示す。求められていない本文は書かない。
- **作成（create）**：構成を考え、本文を完成させ、指定形式で検証・納品する。
- **レビュー（review）**：問題と修正案を報告する。原本と関連ファイルを変更しない。
- **改訂（revise）**：問題を診断し、妥当な内容と編集可能な構造を保って直す。

通常の作成依頼では、設計案だけで止まらず完成まで進める。途中承認はユーザーが求めた
場合に限る。短い文書では設計メモと確認を簡潔にまとめ、独立した設計書や全欄の記入を
要求しない。レビューでは以下を診断の観点として使い、修正・生成の工程は行わない。

## 1. 文書を使う場面と目的をつかむ

提供された素材と、改訂する実際の文書を読む。誰が、いつ、何のために使うのかを捉え、
読み終えて分かるべきこと・できるべきことを定める。初めて読むときに必要な理解と、
後から読み返す場面があればその疑問・作業を考える。読者が内容を覚えて使うのか、
文書を手元で参照するのかも構成へ反映する。

誰の立場で書く文書かも定める。自分用の記録、担当者からの報告、運営者からの案内など、
書き手と読者の関係を、依頼や提供された既存文書から捉える。ユーザーの代わりに書く場合は、
ユーザーがその文書で担う立場に合わせる。チャットの相手と文書の読者を区別し、人称、
丁寧さ、呼びかけの程度を選ぶ。

形式、長さ、必要な内容、読者の前提知識を確認する。指定された文体や文書要件があれば
反映し、読めなかった参照先は適用済みと扱わない。

調べられる事実は調べ、安全に補える条件は明示して進む。成果物を大きく変える未決定事項
だけ確認する。壁打ちを明示された場合は、[質問の進め方](../../references/authoring-interview.md)を使う。

## 2. 記載する内容と条件を整理する

見出しを決める前に、素材全体から読者に伝える答え・主張・事実を選び、短いメモにする。
素材ごとの要約を並べるだけでなく、共通点、違い、因果、依存関係、矛盾を整理する。

- **伝える内容**：読者の理解・判断・作業に必要な情報と、それを支える根拠・出典。
- **一緒に残す条件**：対象、適用条件、例外、数値・単位・期間など、その情報の意味を変えるもの。条件を外して一般化したり、適用範囲を広げたりしない。
- **確度と不足**：観測事実、解釈、仮説、提案を区別し、不明な点は不明のまま残す。素材にない関係や理由を補って整った物語にしない。

元資料にあるだけの情報や重複は除くが、省くと理解や行動が変わる条件は内容と組にして
保持する。メモは設計と照合に使い、完成文書への添付や全項目の表形式化は求めない。

## 3. 読む経路を設計し、内容を配置する

文書名だけで型を決めず、実際の利用目的に当てはまる読み方を選ぶ。
次の目的は組み合わせてよく、作成・レビューなどの動作モードとは別に考える。

| 読者の目的 | 構成で優先すること |
|---|---|
| おおよそを把握する | 要点・全体像を先に示し、必要な詳細を選べる入口を作る |
| 必要な情報を確認する | 疑問や用語から該当箇所を探せ、途中から読んでも分かるようにする |
| 文書を見ながら作業する | 実行順の手順と、その場で必要な条件・確認・失敗時の対応を置く |
| 理解を積み上げる | 前提、理由、例をつなぎ、次の説明を理解できる順序にする |
| 判断・選択する | 求める判断、選択肢や推奨、その根拠と重要な制約を対応させる |

一つの文書でも、事前に概要をつかみ、利用時に必要箇所を確認するなど、場面で読み方が
変わる。必要な経路を両立させ、どこまで読めば何が分かるかを決める。短い案内では
本文だけで足りることもある。独立した要約・目次・付録をすべての文書へ追加しない。
分類の結果は構成に使い、依頼されていない分類表や設計書を成果物へ付けない。

複数の読み方の両立や構成に迷う場合は、[用途に応じた構成の考え方](references/reading-needs.md)の
該当箇所を使う。

手順2の内容を、見出しごとに「読者の問い・作業」「伝える答え」「その条件」が対応する
ように配置する。目次だけで設計を終えず、必要な内容の置き場所まで決める。配置すると
不足や重複が分かる場合は、内容のメモへ戻って整理し直す。

作業順をそのまま説明順にせず、選んだ経路で読者が必要な前提を受け取れるようにつなぐ。
経緯や監査のように時間の順序が情報そのものである場合は保持する。

本文には目的の達成に必要な説明を置く。詳しい方法や記録は注記・付録・既存の参照先へ
回せるが、理解や判断を変える条件・制約と、主張を支える根拠の要約は本文に残す。

概要から詳細へ進む構成では、冒頭に実質的な要点を書き、「何を説明するか」の予告だけで
済ませない。各要点と詳しい説明の見出し・用語を対応させ、関心のある部分を選べるように
する。要点だけで判断を誤らないよう、結論を変える制約は要点の近くにも残す。

参照する箇所には、その疑問や作業に必要な前提・条件を置く。詳しい共通説明は参照先へ
つなげるが、冒頭から読んだり内容を暗記したりしないと使えない状態にしない。要約や
手元での確認に役立つ短い再掲は残し、詳細説明を繰り返し複製しない。

書き始める前に、見出しまたは短いメモで、読む順序と必要箇所へ入る入口を確認する。
各部分の役割とつながりを説明できる構成にし、小さな説明を過剰に章へ分割しない。
設計を共有する必要があれば[設計メモ](assets/text-document-brief.md)を使う。

## 4. 読む・探す・実行する単位で書く

手順1で定めた書き手の立場で本文を書く。敬体・常体の統一だけでなく、報告、提案、指示
など、その文で何を伝えるかに合う語調を選ぶ。たとえば自分用の手順では「受付へ連絡する」、
運営者から利用者への案内では「受付へ連絡してください」と書ける。自分用でも必要な
条件・例外は残す。呼びかけ、励まし、解説は、その関係と用途に役立つ場合に使う。
語調を整えるために、推奨を義務へ変えたり、未確定の内容を断定したりしない。

読者が必要とする用語や前提は、使う時点で渡す。内部識別子や略語を説明の代わりにせず、
何を指すかを示す。名詞の連結、括弧、スラッシュで情報を圧縮しすぎない。一文の中で
複数の判断・条件・例外の対応が追いにくくなったら分ける。専門性や数値の精度は保つ。

段落では、一つの話題を理由・事実・具体例などで掘り下げる。前の文を受けて説明を
進め、主張とその理由、結果とその留保など、一緒に読む必要のある文は同じ段落へ置く。
話題や説明の役割が変わったところで段落を分ける。一文ごとに空行を入れて説明を
細切れにしたり、複数の話題を一つの長い段落へ詰め込んだりしない。短くても一つの役割を
果たす段落はそのままでよい。段落をまたぐ関係は、因果・対比・条件などが分かるように
つなぎ、「次に説明する」という実況や余白だけで済ませない。

説明が抽象的に続くところには、具体例、比較、適用を置いて理解の足場を作る。
見た目の変化のための修辞疑問や休憩文は足さない。結びには、その説明から分かったことや
次に使える理解を残し、本文と関係の薄い一般論で終わらない。

表現形式は、読者が続けて読むのか、項目を拾うのか、同じ軸で見比べるのかで選ぶ。
順に理解する説明は段落にまとめ、個別に確認する条件や実行する手順は拾いやすい形にする。

- **段落**：因果、推論、留保など、一続きに理解する説明。
- **箇条書き**：個別に確認できる選択肢、条件、必要物など。各項目が何の一覧か分かり、同じ粒度で読めるようにする。前の項目を受けて理由や結論へ進む説明は段落にする。
- **番号付きリスト**：順序が意味を持つ手順。実行条件や失敗時の対応は該当する手順に添え、並列項目へ不要な順序を付けない。
- **表**：複数の対象を共通の項目で比較・検索するときに使う。対象ごとに説明内容が異なる場合や、長文のセルを順に読むだけになる場合は、段落やリストを選ぶ。表から読み取るべき違いや判断上の注意は文章で示し、全セルの内容を繰り返さない。

たとえば「申請番号がないと照合できず、審査を始められない」は一続きの説明にし、
「申請番号・本人確認書類・代理申請時の委任状」は必要物の一覧にする。表やリストを
挟んだ後も説明が続くなら、その結果や条件を受けて本文へ戻る。見た目を変えるためだけに
段落・リスト・表を交互に置かない。

見出しは階層と入口、強調は注意を向ける要点に使う。段落全体の太字や強調の連続で
優先順位を失わせない。引用やコードブロックは実際の引用・入力例などに使い、通常の
説明を囲う装飾にしない。

改行は表示結果で判断する。Markdownのソース上の折り返しは、通常、段落の区切りには
ならない。話題の区切りには空行で段落を作り、表示幅に応じた行の折り返しは閲覧環境へ
任せる。`<br>`や行末の二つのスペースなどによる強制改行は、住所など行の区切り自体に
意味がある場合に使う。通常の説明を一文ずつ強制改行したり、空行の数で余白を調整したりしない。
文数・項目数の固定上限を文章品質の基準にしない。

## 5. 想定した使い方で確認し、成果物を届ける

**構成の確認**では、手順3で選んだ読み方を完成文書で試す。該当するものだけ確認する。

- 概要把握：冒頭・見出し・要点だけで、必要な全体像と重要条件が分かるか。
- 参照：代表的な疑問から見出しを選び、答えへ到達できるか。その箇所だけで条件と対応が分かるか。
- 作業：文書を見ながら手順の分岐や終了まで追えるか。
- 学習：前提から説明をたどれ、途中で関係を補って読まなくてよいか。
- 判断：選択肢・根拠・制約を踏まえて判断できるか。

表示された本文も読み、読み返しや探し直しが必要な位置、段落やリストによる分断、
異なる話題の詰め込み、表の比較しにくさ、不自然な改行を確認する。
書き手の立場が本文で一貫し、人称・語尾・呼びかけが手順1で捉えた読者との関係に合うかも確認する。
段落の長さや形式の数だけで採点しない。

**内容の照合**では、手順2のメモと原資料を使い、構成とは別に次を確認する。

- 原資料から完成文書へ：必要な内容が揃い、数値・適用条件・例外・確度が要約や言い換えで落ちていないか。条件は対象の説明から読み取れるか。
- 完成文書から原資料へ：各主張を根拠へ戻せるか。原資料にない理由・保証・規則を補っていないか。

読みやすさを正しさの証明にせず、構成と内容の両方に問題がないことを確認する。

問題があれば作成・改訂では直し、レビューでは位置・読者への影響・原因・具体的な修正案を
優先度順に示す。必要なら構成案も示す。報告を整理する場合は[レビュー用メモ](assets/review-report.md)を使う。

形式固有の生成・render・previewには、利用可能な`documents`等のSkillを使う。指定された
形式を守り、既存の見出しスタイル、表、図、引用、脚注、コメント、変更履歴、リンク、
編集可能な構造を可能な限り保つ。豊かな文書を単純なテキストへ置き換えない。
必要な成果物確認を行って納品し、未検証部分は理由と影響を示す。

設計では構成・情報配置・前提・証拠不足・確認結果を簡潔に返す。作成・改訂では完成した
文書と重要な前提・未解決事項を返し、改訂には変更概要を添える。長い作業ログは付けない。

## 要件に応じた補足

通常は上の手順で進める。必要があるときだけ、該当箇所を参照する。

- [用途に応じた構成の考え方](references/reading-needs.md)：読み方を組み合わせる場合や、用途に合う構成を選びにくい場合の補足。
- [根拠と成果物の確認](references/verification.md)：調査・数値・引用を扱う場合、長い文書の参照構造、ファイル納品の確認。
