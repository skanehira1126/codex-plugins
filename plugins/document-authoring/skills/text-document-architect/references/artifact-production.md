# テキスト成果物の生成と検証

ユーザーが承認した、または素材と安全な合理的前提から確定した文書設計を正本とし、利用可能な形式別ワークフローで成果物を作る。安全に確定できない選択によって成果物が大きく変わる場合だけ、ユーザーへ確認する。

## 共通規則

- 既存の豊かな成果物を、単純なプレーンテキストへ置き換えない。
- 見出し、本文、表、図、引用、注記、Appendixを、同じ支配的な目的と読み方の契約へ揃える。
- スタイルは装飾ではなく、意味構造として使う。
- 内容の正しさと、ファイルとしての完全性を両方確認する。
- PDFや画像だけでなく、編集可能な原本を可能な限り保持する。

## Word・Google Docs形式

- 一貫した論理階層の見出しスタイルを使う。
- 改ページ、孤立見出し、表の分断、過剰な余白、ヘッダー、フッター、ページ番号を制御する。
- 結論、規則、手順と、その根拠または適用条件を近くに置く。
- 表は構造化比較に使い、長い説明文を押し込まない。
- 長さと参照用途に応じて、目次、内部リンク、章の案内を追加する。
- 改訂時は、コメント、変更履歴、参考文献、脚注、編集可能な構造を保つ。
- 環境が対応する場合、最終DOCXをレンダリングし、すべてのページ画像を確認する。
- ユーザーがPDFのみを求めない限り、編集可能なDOCX等も残す。

## Markdown・プレーンテキスト原稿

- 見出し階層を一貫させる。
- リンク、脚注、表を、対象レンダラーで読みやすい形にする。
- 行長や書式規則が、出力先システムを壊さないようにする。
- HTML、PDF、別形式へ変換する場合は、レンダリング結果をプレビューする。
- 変換元Markdownを編集可能な原本として保持する。

## PDF

- PDFは基本的に配布形式として扱い、可能なら編集可能な原本を残す。
- ページをレンダリングし、特に表、図、脚注、改ページ、ブックマークを確認する。
- 再利用やアクセシビリティが重要な場合は、文字選択・検索、リンク動作、読み上げ順を確認する。
- スキャン画像だけのPDFを、編集可能な原本の代替にしない。

## Appendixと参照

- 本文からAppendixを参照する場合は、安定した章名・番号を使う。
- Appendix単独でも、対象、定義、出典が分かるようにする。
- 重要な根拠をAppendixへ移した場合も、本文には理解、判断、作業に必要な要約を残す。
- 目次・内部リンクがある場合、Appendixまで到達できるか確認する。

## 最終確認

1. ファイルが正常に開く。
2. タイトルと見出しが、承認されたアウトラインと一致する。
3. 内容の欠落、文字切れ、不自然な分断がない。
4. 表、図、注記、Appendixが判読でき、正しく参照されている。
5. 引用・出典を人間が追跡できる。
6. 目次、内部リンク、ページ番号、ブックマークが用途に合う。
7. 編集可能な原本が必要な形式で残っている。
8. ファイル名と版が明確である。
