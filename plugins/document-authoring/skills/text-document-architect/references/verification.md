# 根拠と成果物の確認

該当する要件だけを確認する。文書の長さや用途に見合う検証を行い、未確認と不合格を
区別する。本文がない設計段階で、表現や成果物の完成を確認したことにしない。

## 調査・数値・引用を使う場合

一次資料、公式記録、直接データなど、主張を実際に支持する出典を使う。変化し得る
事実は現在の状態を検証し、公開日と出来事・測定の日付を区別する。引用・出典は
対象の主張の近くに置き、ページ番号、引用文、URL、脚注、データを捏造しない。

数値は、指標の定義、単位、対象、分母、期間、比較条件を確認する。たとえば「利用率が
上がった」だけでは、誰が何をどの期間に使った割合か分からない。定義を示し、元の精度を
保った上で説明する。追跡が複雑なら、主張・出典・対象範囲・確度・制約の対応を整理する。

根拠が足りない場合は、主張の範囲を狭める、解釈や仮説として示す、または証拠不足を
明示する。別の集団のベンチマークで穴を埋めない。比較に使うなら比較可能性と限界を示す。
「推定できない」を「効果がない」へ変えるなど、表現改善によって確度を変えない。

## 注記・付録・参照先がある場合

本文には理解・判断・作業に必要な要約を残し、参照先へ移したことで重要な条件が
分からなくなっていないか確認する。付録には内容を特定できる章名を付け、単独でも
対象・定義・出典が分かるようにする。実行ログや識別子の対応表も、追跡に必要なら
ここへ置ける。監査など記録自体が目的の場合は本文に残す。

長い文書は目次や内部リンクから必要箇所に到達できるか試す。参照先が実在し、利用可能か
確認する。読めない参照先を検証済みと扱わない。

## ファイルとして納品する場合

形式固有Skillの技術要件に従い、必要なrenderまたはpreviewで次を確認する。

- ファイルが開き、タイトル・見出し・本文・表・図・注記に欠落がない。
- 文字切れ、表崩れ、不自然な改ページや強制改行がない。
- 結論や手順と、その根拠・適用条件が利用時に分断されていない。
- 目次、引用、内部リンク、ページ番号、ブックマークが正しく機能する。
- 指定形式、必要な編集可能な構造、ファイル名と版が保たれている。

## Markdownの注意箇所を絞り込む場合

必要に応じて`../scripts/lint_text_document.py`を使う。Skillディレクトリからの実行例：

```bash
python scripts/lint_text_document.py path/to/document.md --mode sequential --check-sources
```

参照文書には`--mode reference`、意思決定文書には`--mode decision`を使う。
`--モード 連続読解 --出典確認`などの日本語オプションも使える。lintは確認候補を示すだけで、
論理・読みやすさ・事実性を証明しない。機械的な文字数や項目数の閾値を合否基準にしない。
